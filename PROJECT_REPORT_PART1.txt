CHAPTER 1: ABSTRACT
================================================================================

The Student Placement Cell Database Management System (SPCDBMS) is a full-stack,
role-based web application designed to digitize and streamline the end-to-end
placement process at BML Munjal University. The system eliminates manual,
spreadsheet-driven tracking by replacing it with a centralized relational
database powered by MySQL, accessible through three distinct portals — for
Students, Placement Coordinators, and CGDC Administrators.

The backend is built on Node.js and Express.js, exposing a RESTful API secured
with JWT-based authentication and role-based middleware. The frontend uses Vite
with Vanilla JavaScript and Chart.js for real-time data visualizations. The
database is hosted on Aiven Cloud (managed MySQL).

From a database perspective, the project demonstrates the complete lifecycle of
relational database design — from conceptual ER modeling through physical schema
creation, normalization to Third Normal Form (3NF), and advanced SQL
implementation including multi-table JOINs, correlated subqueries, GROUP BY with
HAVING, aggregate and scalar functions, SQL Views (30+), Stored Procedures,
Triggers, Indexing, and ACID-compliant Transactions.

A bonus ATS (Applicant Tracking System) Resume Analyzer feature was also
implemented, where student resume PDFs are parsed, scored against role-specific
keyword databases, and stored in the RESUME table with keywords_found and
keywords_missing columns.

The system has been tested with real data across 14 core tables and 30+ views,
supporting hundreds of student and coordinator interactions simultaneously.

CHAPTER 5: INTRODUCTION
================================================================================

5.1 Background
--------------
University placement processes have traditionally relied on manual coordination —
students emailing their resumes, coordinators maintaining Excel trackers, and
administrators compiling annual reports by hand. This approach is error-prone,
non-scalable, and provides zero real-time visibility to any stakeholder.

As institutions grow and placement volumes increase, the need for a centralized,
database-driven placement management system becomes critical. The Student
Placement Cell Database Management System (SPCDBMS) addresses this gap by
providing a fully integrated, role-based digital platform.

5.2 Motivation
--------------
The primary motivation for this project is the academic and practical need to
demonstrate a complete, real-world application of relational database concepts —
from conceptual design (ER Diagrams) through physical implementation (MySQL),
including normalization, advanced SQL, and modern web application architecture.

Additionally, the placement process at any engineering institution is a high-stakes
workflow involving multiple stakeholders. Building a system that correctly models
these relationships provides a meaningful, domain-specific context for applying
DBMS principles.

5.3 Objectives
--------------
1. Design a normalized relational schema (up to 3NF) for a multi-role placement
   management system.
2. Implement a complete MySQL database with DDL, DML, DQL, and TCL operations.
3. Demonstrate advanced SQL concepts: JOINs, Subqueries, GROUP BY, HAVING,
   Views, Stored Procedures, Triggers, and Indexing.
4. Build a real-time, role-based web application connected to the MySQL database
   via a RESTful Node.js API.
5. Provide a live SQL Query Explorer within the application for output demonstration.

5.4 Scope
---------
The system covers the following functional areas:
  - Student registration, profile management, and application tracking
  - Job profile management by companies and admins
  - Interview scheduling and management by coordinators
  - Offer issuance and acceptance workflows
  - Real-time analytics dashboards for all three roles
  - ATS-based resume scoring and storage
  - Audit logging via database triggers
  - Role-based authentication using JWT

CHAPTER 6: PROBLEM STATEMENT
================================================================================

6.1 Current State of Placement Management
------------------------------------------
The existing placement process at most universities faces the following critical
challenges:

1. Manual Tracking: Application statuses tracked via Excel sheets lead to data
   inconsistency and duplication. The same student may appear as "placed" in one
   sheet and "active" in another.

2. No Real-Time Visibility: Students have no way to track their application status
   in real-time without calling or emailing the placement office.

3. Data Fragmentation: Student data, company data, job profiles, and placement
   records exist in separate, unconnected documents with no referential integrity.

4. No Audit Trail: There is no historical record of when an application status
   changed or who made the update.

5. Scalability Issues: As student and company counts grow, manual management
   becomes increasingly unsustainable.

6. No Analytics: Administrators have no way to generate real-time insights on
   department-wise placement rates, top-hiring companies, or average packages.

6.2 Proposed Solution
----------------------
The SPCDBMS solves all of the above with:

- A centralized MySQL database with 14 normalized tables and enforced
  referential integrity via Foreign Keys.
- A role-based web portal with three distinct dashboards (Student, Coordinator,
  Admin) providing real-time data visibility.
- A RESTful API with JWT authentication ensuring only authorized users can
  access and modify data.
- Trigger-based automatic audit logging in STATUS_AUDIT_LOG whenever an
  application status is changed.
- 30+ pre-built SQL Views for real-time analytics accessible directly from the
  Admin and Coordinator dashboards.
- A live SQL Query Explorer allowing users to run meaningful queries with
  real output from the production database.

6.3 Key Stakeholders
---------------------
  Stakeholder          | Role in System
  ---------------------|--------------------------------------------------
  Student              | Applies to jobs, tracks status, uploads resume
  Placement Coordinator| Manages assigned students, schedules interviews
  CGDC Admin           | Global oversight, analytics, user/company management
  Company (implicit)   | Represented via COMPANY and JOB_PROFILE tables

CHAPTER 7: METHODOLOGY
================================================================================

7.1 System Architecture
------------------------
The system follows a 3-tier architecture:

Tier 1 — Presentation Layer (Frontend):
  Technology: Vite + Vanilla JavaScript + Chart.js + Ionicons
  Responsibility: Renders role-specific dashboards, handles user interaction,
  makes REST API calls, and displays real-time data from the database.

Tier 2 — Application Layer (Backend):
  Technology: Node.js + Express.js + JWT + mysql2
  Responsibility: Handles HTTP requests, enforces authentication and
  role-based authorization, executes SQL queries via prepared statements,
  and returns JSON responses to the frontend.

Tier 3 — Data Layer (Database):
  Technology: MySQL on Aiven Cloud (Remote)
  Responsibility: Stores all persistent data across 14 normalized tables,
  enforces referential integrity via Foreign Keys, executes Views, Triggers,
  and Stored Procedures.

System Flow:
  [Browser] → HTTP Request → [Express Router] → [Role Middleware] →
  [SQL Query via mysql2] → [MySQL on Aiven] → [JSON Response] → [Browser]

7.2 Development Methodology
-----------------------------
The project followed an iterative, feature-based development approach:

  Phase 1 — Database Design:
    ER Diagram creation → Relational Schema mapping → Normalization (1NF→3NF)
    → DDL (CREATE TABLE statements) → Seed data insertion

  Phase 2 — Backend Development:
    Express server setup → JWT authentication → Role-based route protection
    → API endpoints for all CRUD operations → Views, Procedures, Triggers

  Phase 3 — Frontend Development:
    Vite project setup → Role-based routing (app.js) → Dashboard UIs
    → Chart.js integrations → API integration → Query Explorer panel

  Phase 4 — Testing & Refinement:
    API testing → SQL query validation → UI/UX refinement →
    Performance optimization via indexing

8.4 Handling Many-to-Many (M:N) Relationships
-----------------------------------------------
The relationship between STUDENT and JOB_PROFILE is inherently Many-to-Many:
  - One student can apply to many jobs.
  - One job can receive applications from many students.

In an ER diagram, this is shown with N on both sides of the relationship diamond.
In the relational schema, M:N relationships cannot be directly implemented.
They must be resolved using a BRIDGE (associative) entity.

Resolution:
  The APPLICATION table serves as the bridge entity between STUDENT and JOB_PROFILE.
  It contains:
    - s_id (FK referencing STUDENT)
    - job_id (FK referencing JOB_PROFILE)
    - Additional attributes: applied_date, status, app_deadline

  This converts the M:N into two 1:N relationships:
    STUDENT (1) ——— (N) APPLICATION (N) ——— (1) JOB_PROFILE

9.2 Indexing
-------------
Indexes are created on frequently queried columns to improve performance.

-- Primary index (automatic on all PKs):
   Every PRIMARY KEY auto-creates a B-tree clustered index.
   e.g., STUDENT.s_id, APPLICATION.app_id, COMPANY.comp_id

-- Foreign Key indexes (automatic in MySQL):
   MySQL auto-indexes FK columns for fast join operations.
   e.g., APPLICATION.s_id, APPLICATION.job_id

-- Manual indexes created for performance:
   CREATE INDEX idx_student_dept     ON STUDENT(dept);
   CREATE INDEX idx_student_status   ON STUDENT(profile_status);
   CREATE INDEX idx_app_status       ON APPLICATION(status);
   CREATE INDEX idx_resume_student   ON RESUME(s_id);

   idx_student_dept   — speeds up department-based filtering in dashboards
   idx_student_status — speeds up "placed students" count queries
   idx_app_status     — speeds up application status distribution queries
   idx_resume_student — speeds up ATS score lookups per student


9.3 Normalization
------------------

FIRST NORMAL FORM (1NF):
  Rule: Every column must store exactly ONE atomic value. No lists.

  Violation Found:
    In JOB_PROFILE, the columns:
      required_skills = "Python, Java, SQL"       (comma-separated — NOT atomic)
      eligible_branch = "CS, IT, ECE"             (comma-separated — NOT atomic)

  Fix Applied:
    Created two new tables:

    JOB_REQUIRED_SKILL (job_id, skill_name)
      Each skill is now a separate row.

    JOB_ELIGIBILITY_BRANCH (job_id, branch_name)
      Each branch is now a separate row.

    Similarly, STUDENT.skills (multi-valued) → normalized to STUDENT_SKILL table.
    RESUME.keywords_found and keywords_missing stored as JSON (MySQL native type).

  Result: All tables now satisfy 1NF.

SECOND NORMAL FORM (2NF):
  Rule: Table must be in 1NF, AND every non-key attribute must depend
        on the FULL primary key (not just part of it).
        This applies only to tables with composite primary keys.

  Example — APPLICATION table:
    PK = (app_id) — single column PK, so 2NF is trivially satisfied.
    The columns status, applied_date all depend on app_id alone.

  Example — STUDENT_SKILL table:
    PK = (s_id, skill_name) — composite PK.
    proficiency_level depends on BOTH s_id AND skill_name together.
    (A student may have "Advanced" Python but "Beginner" Java.)
    So no partial dependency. 2NF satisfied. ✅

THIRD NORMAL FORM (3NF):
  Rule: Table must be in 2NF, AND no non-key column should depend
        on another non-key column (no transitive dependencies).

  Potential Violation (hypothetical — we avoided this):
    If we stored coordinator_dept inside STUDENT:
      s_id → coord_id → coordinator_dept (transitive!)
    This is NOT done in our schema.
    coordinator_dept is stored ONLY in PLACEMENT_COORDINATOR.
    STUDENT only stores coord_id (FK). The name is fetched via JOIN.

  Another Example:
    In PLACEMENT_RECORD, the column stream stores the student's department
    at the time of placement. This is intentional "safe redundancy" for
    historical auditing — not a normalization violation.

  Result: All tables satisfy 3NF. No transitive dependencies present.
