SLIDE 7 — KEYS: PK, FK, CANDIDATE (Rubric: Component 5)
=====================================================
Title: "Types of Keys in Our Database"

Primary Key (PK):
  Uniquely identifies each row in a table. Cannot be NULL.
  Examples: s_id in STUDENT, app_id in APPLICATION

Foreign Key (FK):
  Links two tables together. References a PK in another table.
  Examples:
    APPLICATION.s_id  →  STUDENT.s_id
    APPLICATION.job_id →  JOB_PROFILE.job_id
    STUDENT.coord_id  →  PLACEMENT_COORDINATOR.coord_id

Candidate Key:
  Any column that COULD be the Primary Key (unique + not null).
  In STUDENT: both s_id and email can uniquely identify a student.
  s_id is chosen as PK. email is the candidate / alternate key.

Composite Key:
  A PK made of TWO columns together. Used in STUDENT_SKILL:
  Primary Key = (s_id + skill_name) together → unique per student per skill.

SLIDE 9 — NORMALIZATION: 1NF (Rubric: Component 4)
=====================================================
Title: "Normalization — First Normal Form (1NF)"

Rule: Every column must store ONE value only (atomic values).
      No comma-separated lists, no arrays.

BEFORE (Violation):
  JOB_PROFILE table had:
    required_skills = "Python, Java, SQL"      ← NOT atomic!
    eligible_branch = "CS, IT, ECE"            ← NOT atomic!

AFTER (Fixed):
  Created two new separate tables:

  JOB_REQUIRED_SKILL           JOB_ELIGIBILITY_BRANCH
  ┌─────────┬───────────┐      ┌─────────┬─────────────┐
  │ job_id  │ skill_name│      │ job_id  │ branch_name │
  ├─────────┼───────────┤      ├─────────┼─────────────┤
  │   25    │  Python   │      │   25    │     CS      │
  │   25    │  Java     │      │   25    │     IT      │
  │   25    │  SQL      │      │   25    │     ECE     │
  └─────────┴───────────┘      └─────────┴─────────────┘

Result: Each cell now has ONE atomic value. 1NF achieved.

Also: skills in STUDENT → normalized to STUDENT_SKILL table.

SLIDE 10 — NORMALIZATION: 2NF & 3NF (Rubric: Component 4)
=====================================================
Title: "2NF & 3NF — Removing All Redundancy"

2NF — No Partial Dependency:
  Rule: Every non-key column must depend on the WHOLE primary key.
  Applies when PK is composite (multiple columns).

  Example: In APPLICATION, the columns status and applied_date
  depend on BOTH s_id AND job_id together — not just one of them.
  So APPLICATION satisfies 2NF. ✅

3NF — No Transitive Dependency:
  Rule: Non-key columns must NOT depend on other non-key columns.

  VIOLATION EXAMPLE (hypothetical):
    If we stored coordinator_name inside STUDENT, that would mean:
    s_id → coord_id → coordinator_name (transitive!)

  OUR FIX:
    coordinator_name is stored ONLY in PLACEMENT_COORDINATOR.
    STUDENT only stores coord_id (FK). Name is fetched via JOIN.
    So no transitive dependency. 3NF achieved. ✅

Summary:
  1NF: Atomic values ✅
  2NF: Full dependency on PK ✅
  3NF: No transitive dependency ✅

SLIDE 13 — DQL & TCL (Rubric: Component 6)
=====================================================
Title: "DQL & TCL — Querying & Controlling Transactions"

DQL (Data Query Language) — Reading data:
  SELECT s_name, dept, cgpa
  FROM STUDENT
  WHERE profile_status = 'placed'
  ORDER BY cgpa DESC
  LIMIT 10;

  → Fetches top 10 placed students sorted by CGPA.

TCL (Transaction Control Language):
  START TRANSACTION;
    UPDATE OFFER SET offer_status = 'accepted' WHERE offer_id = 12;
    UPDATE STUDENT SET profile_status = 'placed' WHERE s_id = 101;
    INSERT INTO PLACEMENT_RECORD (s_id, comp_id, salary_offered)
    VALUES (101, 5, 12.5);
  COMMIT;   -- saves all 3 changes together
  -- OR --
  ROLLBACK; -- undoes all if any step fails

  TCL Commands used: START TRANSACTION, COMMIT, ROLLBACK

SLIDE 14 — JOINS (Rubric: Component 7)
=====================================================
Title: "SQL Joins — Combining Tables"

INNER JOIN (only matching rows):
  SELECT a.applied_date, c.comp_name, j.role, a.status
  FROM APPLICATION a
  JOIN JOB_PROFILE j ON a.job_id = j.job_id
  JOIN COMPANY c ON j.comp_id = c.comp_id
  WHERE a.s_id = 101;
  → 3-table join showing student's full application journey.
  → Used in: Student Dashboard "My Application Journey"

LEFT JOIN (all rows from left, NULLs if no match):
  SELECT s.s_name, pc.name AS coordinator_name
  FROM STUDENT s
  LEFT JOIN PLACEMENT_COORDINATOR pc ON s.coord_id = pc.coord_id;
  → Students WITHOUT a coordinator still appear (with NULL for name).
  → Used in: Admin Panel Master Student Directory

Why LEFT JOIN here?
  Some students may not yet be assigned a coordinator.
  INNER JOIN would HIDE those students. LEFT JOIN keeps them visible.

SLIDE 15 — GROUP BY & HAVING (Rubric: Component 8)
=====================================================
Title: "GROUP BY & HAVING — Grouped Analysis"

Simple rule:
  WHERE  → filters rows BEFORE grouping
  HAVING → filters groups AFTER GROUP BY

Example 1 — Coordinator Workload:
  SELECT pc.name, COUNT(*) AS student_count
  FROM PLACEMENT_COORDINATOR pc
  JOIN STUDENT s ON s.coord_id = pc.coord_id
  GROUP BY pc.coord_id, pc.name
  HAVING COUNT(*) > 5
  ORDER BY student_count DESC;
  → "Show coordinators managing MORE than 5 students"

Example 2 — Active Major Recruiters (used in Query Explorer):
  SELECT comp_name
  FROM COMPANY
  WHERE comp_id IN (
    SELECT comp_id FROM JOB_PROFILE
    GROUP BY comp_id
    HAVING COUNT(*) > 1
  );
  → "Companies that posted MORE than 1 job"

SLIDE 16 — SUBQUERIES (Rubric: Component 9)
=====================================================
Title: "Subqueries — Queries Inside Queries"

Type 1: Scalar Subquery (returns single value):
  SELECT comp_name, avg_package_offered
  FROM COMPANY
  WHERE avg_package_offered > (SELECT AVG(avg_package_offered) FROM COMPANY)
  ORDER BY avg_package_offered DESC;
  → Inner query calculates global average.
  → Outer query shows companies ABOVE that average.

Type 2: IN Subquery (returns a list):
  SELECT dept, COUNT(*) AS placed_count
  FROM STUDENT
  WHERE s_id IN (SELECT s_id FROM PLACEMENT_RECORD WHERE status = 'confirmed')
  GROUP BY dept;
  → "Which departments have confirmed placements?"

Type 3: Correlated Subquery (references outer query):
  SELECT j.role, c.comp_name
  FROM JOB_PROFILE j JOIN COMPANY c ON j.comp_id = c.comp_id
  JOIN STUDENT s ON s.s_id = 101
  WHERE j.eligibility_cgpa <= s.cgpa
  AND j.job_id NOT IN (SELECT job_id FROM APPLICATION WHERE s_id = s.s_id);
  → "Jobs I qualify for but haven't applied to yet"

SLIDE 17 — FUNCTIONS (Rubric: Component 10)
=====================================================
Title: "SQL Functions — Aggregate & Scalar"

Aggregate Functions (work on a GROUP of rows):
  COUNT(*)           → Total number of applications
  AVG(cgpa)          → Average CGPA per department
  MAX(salary_offered)→ Highest salary from a company
  MIN(ats_score)     → Lowest resume score
  SUM(package)       → Total package value of open jobs

  Example:
    SELECT dept, COUNT(*) AS total, AVG(cgpa) AS avg_cgpa
    FROM STUDENT GROUP BY dept;

Scalar Functions (work on ONE value at a time):
  DATE_FORMAT(recorded_on, '%b') → Shows "Jan", "Feb" for trend charts
  COALESCE(dept, 'Unknown')      → Replace NULL with 'Unknown'
  LPAD(s_id, 4, '0')             → Formats ID as 0001, 0042
  ROUND(salary, 2)               → Rounds salary to 2 decimal places
  UPPER(s_name)                  → Converts name to uppercase

SLIDE 18 — VIEWS (Rubric: Component 11)
=====================================================
Title: "Views — Virtual Tables for Simplicity"

What is a View?
  A saved SELECT query that behaves like a table.
  Hides complexity. Provides a clean interface to the data.
  Our project has 30+ views.

Key Views used in dashboards:
  vw_placement_rate_per_dept     → % placed per department (Admin chart)
  vw_student_placement_status    → Every student's current stage
  vw_top_hiring_companies        → Companies ranked by placement count
  vw_student_readiness           → Students eligible but not yet placed
  vw_avg_ats_by_dept             → Average resume ATS score per department

Example (create one view):
  CREATE VIEW vw_placed_students AS
    SELECT s.s_name, s.dept, c.comp_name, pr.salary_offered
    FROM STUDENT s
    JOIN PLACEMENT_RECORD pr ON s.s_id = pr.s_id
    JOIN COMPANY c ON pr.comp_id = c.comp_id;

  Then just query it as:
    SELECT * FROM vw_placed_students;

SLIDE 19 — STORED PROCEDURES (Rubric: Component 12)
=====================================================
Title: "Stored Procedures — Reusable DB Logic"

What is a Stored Procedure?
  Pre-compiled SQL code stored IN the database.
  Called by name with parameters. Like a function in programming.

Benefits:
  • Encapsulates complex logic inside the database
  • Reduces repeated queries from the server
  • Can include IF/ELSE, loops, error handling

Our Project Uses Procedures For:
  1. GetCoordinatorStats(coord_id)
     → Returns total students, placed count, active applications in 1 call

  2. MarkStudentPlaced(s_id, comp_id, salary)
     → Updates STUDENT status + inserts into PLACEMENT_RECORD atomically

Example:
  DELIMITER //
  CREATE PROCEDURE GetCoordinatorStats(IN cid INT)
  BEGIN
    SELECT COUNT(*) AS total FROM STUDENT WHERE coord_id = cid;
    SELECT COUNT(*) AS placed FROM STUDENT
      WHERE coord_id = cid AND profile_status = 'placed';
  END //
  DELIMITER ;

  -- Call it:
  CALL GetCoordinatorStats(3);

SLIDE 20 — TRANSACTIONS: ACID (Rubric: Component 13)
=====================================================
Title: "Transactions — ACID Properties"

ACID stands for:
  A — Atomicity:   All steps succeed OR none of them do.
  C — Consistency: DB always moves from one valid state to another.
  I — Isolation:   Two concurrent transactions don't interfere.
  D — Durability:  Once committed, changes survive crashes.

Real Example from our project — Accepting a Job Offer:
  (3 things must happen together, or not at all)

  START TRANSACTION;

    -- Step 1: Accept the offer
    UPDATE OFFER SET offer_status = 'accepted' WHERE offer_id = 12;

    -- Step 2: Mark student as placed
    UPDATE STUDENT SET profile_status = 'placed' WHERE s_id = 101;

    -- Step 3: Record the placement
    INSERT INTO PLACEMENT_RECORD (s_id, comp_id, salary_offered, academic_year)
    VALUES (101, 5, 12.5, 2025);

  COMMIT;    -- All 3 saved permanently

  -- If ANY of the above fails → ROLLBACK → DB stays exactly as before.

SLIDE 21 — TRIGGERS & AUDIT LOG (Rubric: Component 14)
=====================================================
Title: "Triggers — Automatic Database Actions"

What is a Trigger?
  SQL code that runs AUTOMATICALLY when a table is changed.
  No manual call needed. Fires on INSERT, UPDATE, or DELETE.

Our 3 Triggers:

  1. AFTER UPDATE on APPLICATION
     → When status changes, auto-inserts a row in STATUS_AUDIT_LOG.
     → This creates a complete history of every status change.

  2. AFTER INSERT on APPLICATION
     → Logs the initial "applied" event in STATUS_AUDIT_LOG.

  3. AFTER UPDATE on OFFER
     → When offer is 'accepted', auto-updates student's profile_status
       to 'placed' in the STUDENT table.

Example:
  CREATE TRIGGER log_status_change
  AFTER UPDATE ON APPLICATION
  FOR EACH ROW
  BEGIN
    IF NEW.status != OLD.status THEN
      INSERT INTO STATUS_AUDIT_LOG(app_id, old_status, new_status, changed_at)
      VALUES (NEW.app_id, OLD.status, NEW.status, NOW());
    END IF;
  END;

SLIDE 22 — INDEXING (Rubric: Component 14)
=====================================================
Title: "Indexing — Making Queries Faster"

What is an Index?
  A separate data structure that lets MySQL find rows MUCH faster.
  Like the index at the back of a textbook — jump straight to the page.

Without Index:  MySQL scans every row (slow for large tables).
With Index:     MySQL jumps directly to matching rows (fast).

Types in our project:

  1. Primary Index (automatic):
     Every PRIMARY KEY auto-creates an index.
     e.g., STUDENT.s_id, APPLICATION.app_id

  2. Foreign Key Index (automatic):
     MySQL auto-indexes FK columns for fast joins.
     e.g., APPLICATION.s_id, APPLICATION.job_id

  3. Manual Index (for performance):
     CREATE INDEX idx_student_dept ON STUDENT(dept);
     → Used when we often filter students by department.

     CREATE INDEX idx_app_status ON APPLICATION(status);
     → Used when we often filter applications by status.

Trade-off: Indexes speed up SELECT but slightly slow down INSERT/UPDATE.

VIVA QUICK REFERENCE
-----------------------------------------------------

Q: Difference between WHERE and HAVING?
A: WHERE filters rows BEFORE grouping. HAVING filters groups AFTER
   GROUP BY. You CANNOT use aggregate functions (like COUNT) in WHERE.

Q: What is a candidate key?
A: Any column that COULD uniquely identify a row and be the PK.
   In STUDENT: s_id and email are both candidate keys. s_id is chosen
   as PK. email becomes the alternate/candidate key.

Q: Difference between INNER JOIN and LEFT JOIN?
A: INNER JOIN returns only rows that have a MATCH in both tables.
   LEFT JOIN returns ALL rows from the left table, even if no match.
   We use LEFT JOIN for students without coordinators — they still show.

Q: What is 2NF?
A: Table is in 2NF if it's in 1NF AND every non-key column depends on
   the FULL primary key, not just part of it. Matters for composite PKs.

Q: Can you INSERT data through a View?
A: Only simple views (single table, no GROUP BY, no aggregation).
   Complex views with JOINs or GROUP BY do NOT support INSERT.

Q: What fires a trigger?
A: INSERT, UPDATE, or DELETE events on a table. We use AFTER UPDATE
   on APPLICATION to log every status change to STATUS_AUDIT_LOG.

Q: Difference between DELETE and TRUNCATE?
A: DELETE removes specific rows, can be rolled back, is logged row by row.
   TRUNCATE removes ALL rows at once, cannot be rolled back, is faster.
