# 📊 Database Normalization Action Plan

Based on the latest schema analysis, audits, and planned feature additions, the `placement_cell_db` database requires the following immediate structural changes to ensure strict compliance with database normalization forms (1NF, 3NF, BCNF).

---

## 1. Functional Redundancies (BCNF / 3NF Violations)

**Issue:** The `USER_ROLE` table contains duplicate columns `role` and `entity_type` which store the exact same business logic (identifying whether a user is a student, coordinator, or admin). This duplicate storage causes potential update anomalies and violates Boyce-Codd Normal Form (BCNF).

**Required Action:**
- Consolidate these columns. 
- Drop the redundant column (e.g., `entity_type`) and use a single `role` column to represent the user's role across the entire system.

---

## 2. Transitive Dependencies (3NF Violations)

### A. Student Resumes
**Issue:** A recent database upgrade synced `r.file_url` from the `RESUME` table directly into an `s.resume_url` column inside the `STUDENT` table. Storing the exact same URL in both places creates a transitive dependency (`STUDENT` -> `RESUME` -> `file_url`).

**Required Action:**
- Drop the `resume_url` column from the `STUDENT` table.
- Enforce a standard `JOIN` with the `RESUME` table whenever a student's file URL needs to be fetched.

### B. Placement Streams
**Issue:** The `PLACEMENT_RECORD` table stores the student's department/stream alongside their `s_id`. Because `s_id` is already a foreign key, the `stream` can be derived transitively by joining `STUDENT.dept`. 

**Required Action:**
- To be strictly 3NF-compliant, drop the `stream` column from `PLACEMENT_RECORD`. *(Note: While past documentation justified this as a "safe redundancy" for taking historical snapshots, strict 3NF compliance demands its removal).*

## 3. Derived Data Risks (Integrity & Redundancy)

Normalization theory strongly discourages storing derived attributes as hard-coded columns, because they frequently lead to out-of-sync data anomalies. 

### A. Company Packages
**Issue:** The `COMPANY` table contains an `avg_package_offered` column. Currently, this is hard-updated with static data. It is a derived attribute that easily mismatches the actual sums of the `OFFER` or `JOB_PROFILE` tables.

**Required Action:**
- Drop the `avg_package_offered` column from `COMPANY`. 
- Create a SQL View (e.g., `vw_company_stats`) that calculates `AVG(package)` dynamically via runtime SQL queries.

### B. Visit Histories
**Issue:** The `COMPANY_VISIT_HISTORY` table stores a static `students_placed` column. Consistency audits have already flagged critical mismatches between this summary column and the actual rows inside `PLACEMENT_RECORD`.

**Required Action:**
- Drop the `students_placed` column entirely.
- Utilize a SQL View to aggregate this `COUNT()` dynamically, ensuring it is always 100% accurate.

## 4. Multi-Valued Attributes (1NF Violations)

**Issue:** The `RESUME_ANALYSIS` table (planned for the upcoming ATS feature in `DATABASE_CHANGES_REQUIRED.md`) proposes using `JSON` arrays to store lists inside the `keywords_found` and `keywords_missing` columns. Storing arrays or lists within a single column is a strict violation of First Normal Form (1NF).

**Required Action:**
- Before deploying the ATS feature, fully normalize it by creating a dedicated child mapping table (e.g., `RESUME_ANALYSIS_KEYWORD`).
- It should contain columns like `analysis_id`, `keyword`, and `status ENUM('found', 'missing')`. This ensures each parsed keyword is completely atomic (one per row).
