3. LOCKING PROTOCOLS & TRANSACTION DESIGN

   What: How to prevent race conditions and ensure data consistency
   Why: Multiple coordinators/students accessing system simultaneously
   
   AI Showed:
   • Pessimistic locking examples (SELECT...FOR UPDATE)
   • Transaction isolation levels
   • Deadlock prevention techniques
   • ACID property implementations
   
   How We Applied:
   • Studied locking patterns from real database systems
   • Applied SELECT...FOR UPDATE in offer acceptance workflow
   • Lock JOB_PROFILE vacancy before decrement
   • Bulk coordinator re-assignment locks 150+ student rows
   
   Example - Offer Acceptance:
     BEGIN;
     SELECT vacancies FROM JOB_PROFILE WHERE job_id=5 FOR UPDATE;
     ↑ LOCK activated (other sessions wait)
     UPDATE JOB_PROFILE SET vacancies=vacancies-1;
     COMMIT;
     
   Problem Solved:
   ✓ Two students accept offer simultaneously for last vacancy
   ✓ Session 1 locks row → vacancies becomes 0 → accepts successfully
   ✓ Session 2 waits for lock → vacancies already 0 → acceptance fails
   ✓ No race condition, no negative vacancy

4. TRANSACTION MANAGEMENT & ATOMIC OPERATIONS

   What: How to ensure multi-step operations succeed completely or fail completely
   Why: Offer acceptance requires updating 3+ tables atomically
   
   AI Showed:
   • BEGIN/COMMIT/ROLLBACK patterns
   • Transaction isolation levels
   • Atomicity guarantees
   • Error handling in transactions
   
   How We Applied:
   • Created sp_accept_offer stored procedure
   • All steps in single transaction:
       1. UPDATE OFFER status='accepted'
       2. UPDATE STUDENT status='placed'
       3. INSERT PLACEMENT_RECORD
       4. INSERT STATUS_AUDIT_LOG
   • If any step fails → ROLLBACK all steps
   
   Benefit:
   ✓ Cannot have offer accepted without placement record
   ✓ Cannot have student marked placed without offer
   ✓ All 4 steps guaranteed to complete together

─────────────────────────────────────────────────────────────────────────────

Locking Protocol Example:

  Problem: Two students accept offer for last vacancy
  
  Without Locking:
    Session 1: SELECT vacancies=1 ✓
    Session 2: SELECT vacancies=1 ✓
    Session 1: UPDATE vacancies=0
    Session 2: UPDATE vacancies=-1 ✗ CORRUPTED
    
  With Locking (AI showed pattern):
    Session 1: SELECT vacancies FOR UPDATE (lock acquired)
    Session 2: SELECT vacancies FOR UPDATE (waits...)
    Session 1: UPDATE vacancies=0 → COMMIT (lock released)
    Session 2: SELECT vacancies FOR UPDATE (lock now acquired, value=0)
    Session 2: CHECK IF vacancies>0 → NO → Reject acceptance
    
  Result: Only one accepted, data integrity maintained

─────────────────────────────────────────────────────────────────────────────

ATS Integration Example:

  Problem: How to efficiently search 100,000 resumes by skill?
  
  Without (Full-text scan): 8 seconds per search
  
  AI showed normalization pattern:
    Resume uploaded → NLP extracts keywords → Store in separate table
    Search query → JOIN with indexed table → Results instant
  
  Our Implementation:
    CREATE TABLE RESUME_PARSED_KEYWORD (
      resume_id INT,
      keyword VARCHAR(100),
      frequency INT,
      PRIMARY KEY (resume_id, keyword),
      INDEX idx_keyword (keyword)
    );
    
    Query: SELECT * FROM RESUME
           JOIN RESUME_PARSED_KEYWORD ON RESUME.resume_id = RESUME_PARSED_KEYWORD.resume_id
           WHERE keyword='Python';
    
  Result: "Find resumes with Python" → 0.15 seconds (vs. 8 seconds)

KEY LEARNINGS APPLIED TO PROJECT
─────────────────────────────────────────────────────────────────────────────

1. Atomicity is Critical
   ✓ Multi-step operations must succeed together
   ✓ Applied: sp_accept_offer wraps 4 operations in one transaction
   ✓ Prevents: Half-complete data states

2. Locking Prevents Race Conditions
   ✓ Shared resource access needs mutual exclusion
   ✓ Applied: FOR UPDATE on JOB_PROFILE, STUDENT tables
   ✓ Prevents: Double-overbooking, conflicting updates

3. Real-Time Requires Event-Driven Architecture
   ✓ Database changes must trigger actions (not polling)
   ✓ Applied: Triggers fire on INSERT/UPDATE
   ✓ Result: Notifications pushed instantly

4. Data Structure Enables Features
   ✓ Separate tables allow indexed searching (1NF)
   ✓ Applied: RESUME_PARSED_KEYWORD enables skill search
   ✓ Without: Search would be slow and unreliable

5. Persistence Matters
   ✓ Transaction data survives application crashes
   ✓ Applied: STATUS_AUDIT_LOG maintains immutable change history
   ✓ Protected: Even if app crashes, audit trail is safe
